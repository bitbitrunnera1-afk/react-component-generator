# commit

변경사항을 분석해 컨벤션에 맞게 커밋한다. 사용자 승인 절차 없이 바로 커밋하고, 결과를 보고한다.

## 절차

### 1. 변경사항 분석

아래 명령을 병렬로 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # 스테이지되지 않은 변경
git diff --staged   # 이미 스테이지된 변경
git log --oneline -10   # 기존 메시지 스타일 참고
```

- 커밋할 변경이 없으면 그 사실만 알리고 끝낸다.
- git 저장소가 아니면 알리고 끝낸다. `git init`은 사용자가 요청할 때만 한다.
- 기본 브랜치(main/master)에 있으면 변경 내용에 맞는 이름(예: `feat/retro-theme`)으로 새 브랜치를 만들고 그 위에 커밋한다.
- 새로 추가된(untracked) 파일도 내용을 읽어 변경 목적을 파악한다.

### 2. 논리적 단위로 분류

- 하나의 커밋에는 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 같은 목적에 속한 파일(구현, 테스트, 스타일)은 함께 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`는 대화형이라 쓸 수 없다. 이 경우 한 커밋으로 묶고 그 사실을 사용자에게 알린다.
- 아래 파일은 커밋 대상에서 제외하고 사용자에게 알린다.
  - 비밀 정보: `.env`, 키, 토큰, 자격 증명 파일
  - 빌드 산출물과 의존성: `node_modules/`, `dist/`
  - 에디터, OS 임시 파일

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

- **type**
  - `feat`: 사용자에게 보이는 새 기능이나 화면 변경
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 구조 개선
  - `chore`: 설정, 의존성, 문서, 스킬 등 부수 작업
- **요약**
  - 한국어로 쓴다.
  - 50자 안팎의 한 줄로 쓰고 마침표는 붙이지 않는다.
  - "무엇을 했는가"를 현재형 동사로 쓴다. 예: `feat: 레트로 데스크톱 테마로 전체 UI 개편`
- **본문**
  - 요약만으로 "왜"가 전달되지 않을 때만 쓴다.
  - 변경 이유와 영향을 2~3줄 이내로 쓴다.
- 이 세션의 시스템 안내에 커밋 attribution 줄이 지정되어 있으면 본문 맨 끝에 그대로 덧붙인다.

### 4. 커밋 실행

사용자 승인을 기다리지 않고 분류한 커밋 단위대로 바로 커밋한다. 커밋을 마친 뒤 아래 내용을 보고한다.

1. 만든 커밋 목록(해시, 메시지)
2. 각 커밋에 포함된 파일
3. 제외한 파일과 그 이유

커밋 실행 규칙:
- 파일은 `git add -A`나 `git add .` 대신 이름을 지정해 스테이지한다.
- 여러 줄 메시지는 heredoc으로 전달한다.
- `--no-verify`, `--amend`, `--force`는 사용자가 명시적으로 요청하지 않으면 쓰지 않는다.
- pre-commit 훅이 실패하면 원인을 수정한 뒤 **새 커밋**을 만든다. 훅을 우회하지 않는다.
- 커밋이 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여준다. push는 하지 않는다.
